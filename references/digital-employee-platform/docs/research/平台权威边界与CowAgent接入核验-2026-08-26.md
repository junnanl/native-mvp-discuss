## 3. 核心结论：按事实类型划分权威

不能选一个组件作为所有信息的“全局唯一权威”。可靠的边界是：

| 事实类型 | 权威方 | 具体内容 |
| --- | --- | --- |
| 产品与业务事实 | StaffDeck | 用户、租户、员工、业务任务、产品权限、A2UI 策略、业务审计与页面投影 |
| 平台运行事实 | dsh 及项目自有运行插件 | `executionRunId`、规范事件、平台序号、取消/超时/幂等、运行状态机和持久运行记录 |
| 原始执行事实 | CowAgent | 模型实际输出、工具调用和结果、记忆/知识检索、子 Agent、生成文件和原始错误 |
| 长任务治理事实 | 唯一 Loop owner | Goal、轮次、预算、证据、Gate、停止条件与下一次唤醒；当前只保留候选结论 |

最准确的表述是：

> CowAgent 是原始执行事实来源；dsh 是平台接受后的规范运行记录权威；StaffDeck 是产品业务权威。

dsh 不应凭空发明 CowAgent 没有提供的事实。规范事件必须保留来源信息，例如 `providerRunId`、
`providerSequence`、原始事件类型、观测时间和原始载荷引用，以便追溯映射是否正确。

## 4. 三个组件的定位和替换边界

推荐的完整平台结构是：

```text
StaffDeck 后端（产品应用，不是 dsh 插件）
  -> dsh digital-employee-runtime 插件
       -> ExecutionProvider 合同
            -> CowAgentExecutionProvider
                 -> CowAgent 2.1.7
```

事件方向相反：

```text
CowAgent 原始事件
  -> CowAgentExecutionProvider 映射
  -> dsh 规范事件 + Run Ledger
  -> StaffDeck 查询、SSE 展示和业务审计投影
```

定位结论：

- StaffDeck 不应作为 dsh 插件。它是面向用户的产品应用，通过后端调用 dsh 的稳定平台接口。
- CowAgent 应通过 dsh 插件中的 `ExecutionProvider` 适配，不允许 StaffDeck 业务代码直接依赖 CowAgent 私有类型。
- dsh 是当前锁定的运行时核心和插件宿主，不是普通透明转发层。
- 真正的平台核心不是“裸 dsh”，而是“锁定的 dsh rc2 + 项目自有执行合同和 Run Ledger 插件”。

替换含义：

- 更换 CowAgent：新增另一个 `ExecutionProvider` 实现，不改产品业务合同。
- 更换 StaffDeck：更换产品应用或消费者，继续消费稳定的执行合同。
- 更换 dsh：当前一期不支持，属于平台级迁移，而不是普通 Provider 或 UI 替换。

“dsh 永远不能替换”不是技术事实。dsh 当前仍是 Developer Preview，Session format 固定为 `0`，不承诺
广泛兼容。长期应锁定项目自己的 `Execution API v1`，避免 StaffDeck 直接依赖 dsh 私有类型。

## 5. ID、事件和运行状态边界

完整平台需要保留三层 ID：

| ID | 所有者 | 用途 |
| --- | --- | --- |
| `businessRunId` | StaffDeck | 关联员工、用户、租户和业务任务 |
| `executionRunId` | dsh 运行插件 | 平台运行身份、查询、取消、事件和终态 |
| `request_id` / `session_id` | CowAgent | Provider 私有关联和对话上下文，只保存在适配器映射中 |

CowAgent 的请求内 `seq` 是短期 SSE 重放游标，不能直接作为平台事件序号。dsh 应为接受的规范事件重新分配
单调 `sequence`，同时保存 CowAgent 的 `providerSequence`。

若恢复完整平台路线，项目拥有的最小执行合同应表达：

```text
start(request) -> executionRunId
events(executionRunId, cursor) -> ordered events
inspect(executionRunId) -> current snapshot
cancel(executionRunId, reason) -> cancellation request
artifact(executionRunId, artifactId) -> controlled access
```

## 6. CowAgent 2.1.7 接口核验

### 6.1 当前公开给本地集成的实际边界

CowAgent 的 [`API_CALLING.md`](/home/liujunnan/gs-ai/QwenPaw+cowagent/API_CALLING.md:3) 明确说明：当前是 Web

```text
GET /stream?request_id=... -> SSE
POST /cancel -> 请求取消
POST /upload -> 上传附件
GET /api/file?path=... -> 下载文件
```

对应文档见
[`API_CALLING.md:39`](/home/liujunnan/gs-ai/QwenPaw+cowagent/API_CALLING.md:39) 和
[`API_CALLING.md:208`](/home/liujunnan/gs-ai/QwenPaw+cowagent/API_CALLING.md:208)。

### 6.2 Web SSE 事件

WebChannel 会将 CowAgent 内部事件映射为：

```text
delta
reasoning
phase
tool_start
tool_progress
tool_end
subagent_step
message_end
file
image
artifact
done
cancelled
stream_end
```

映射实现见
[`web_channel.py:911`](/home/liujunnan/gs-ai/QwenPaw+cowagent/delivery/offline-install/patch-mounted/frontend/channel/web/web_channel.py:911)。

重要限制：

- reasoning 对前端流最多发送约 4 KiB。
- 工具展示结果约 32 KiB，普通工具结果摘要约 2 KiB。
- `done` 不是可靠的“业务成功”事件；错误也会被包装为带错误文本的 `done`。
- `stream_end` 只表示 SSE 传输结束，不代表运行成功。
- 当前 Web 事件是浏览器展示合同，不是稳定的平台运行合同。

### 6.3 SSE 重放能力及其边界

CowAgent 为每个 `request_id` 维护带 `seq` 的内存事件日志，支持 `after_seq` 和 `Last-Event-ID` 重连，光标
失效时返回 `resync_required`。实现见
[`web_channel.py:692`](/home/liujunnan/gs-ai/QwenPaw+cowagent/delivery/offline-install/patch-mounted/frontend/channel/web/web_channel.py:692)
和
[`web_channel.py:1655`](/home/liujunnan/gs-ai/QwenPaw+cowagent/delivery/offline-install/patch-mounted/frontend/channel/web/web_channel.py:1655)。

该日志的边界是：

- 每个请求最多约 5000 条事件或 4 MiB。
- 只存在于 CowAgent 进程内，服务重启后不能作为平台持久事实。
- 完成后只保留短暂 tail grace；空闲流也会被回收。
- 它适合实时展示和短时重连，不适合完整审计或跨进程恢复。

### 6.4 取消语义反例

实机测试得到过以下顺序：

```text
POST /cancel -> {"status":"success","cancelled":1}

SSE:
cancelled
done
stream_end
```

源码证明第一个 `cancelled` 不是可靠终态：

1. `/cancel` 只是在取消注册表中设置标志；即使没有运行中的任务，接口也按幂等方式返回成功。
2. `/cancel` handler 会立即向 SSE 发布 `cancelled`，此时 Agent 可能尚未运行到取消检查点。
3. 真正的执行器只在轮次开始、工具之间或流式 chunk 等安全点检查取消。
4. Agent 真正捕获取消后，内部还会再发送 `agent_cancelled`，WebChannel 又把它映射成同名 `cancelled`。
5. 随后仍可能出现包含部分答案或错误文本的 `done`，最后才是 `stream_end`。

关键实现见
[`web_channel.py:1049`](/home/liujunnan/gs-ai/QwenPaw+cowagent/delivery/offline-install/patch-mounted/frontend/channel/web/web_channel.py:1049)
和
[`web_channel.py:1758`](/home/liujunnan/gs-ai/QwenPaw+cowagent/delivery/offline-install/patch-mounted/frontend/channel/web/web_channel.py:1758)。

因此完整平台不能直接采用“第一个终态事件获胜”。正确模型应至少区分：

```text
running -> cancel_requested -> cancelled
running -> succeeded | failed | timed_out
```

原始 CowAgent `cancelled` 只能先解释为 `cancel_requested`。只有收到可确认的执行器取消结果，或按平台明确定义
的收束规则完成后，dsh 才能提交唯一平台终态。若当前 Web API 无法可靠区分两种 `cancelled`，恢复完整平台
路线时必须在 CowAgent shim 或 Provider 中补充明确的 terminal outcome。

### 6.5 工具、记忆和产物

- 工具调用可通过 `tool_start/progress/end` 观察，但 WebChannel 会截断展示载荷。
- 记忆检索不是独立公开运行 API；运行中调用 `memory_search` 时只表现为普通工具事件。
- CowAgent 是“是否真的调用工具、检索记忆、生成文件”的事实来源。
- `file_to_send` 可能提供 CowAgent 容器内绝对路径，WebChannel 再生成 `/api/file?path=...`。
- 平台不能把 CowAgent 绝对路径直接保存为产品下载地址。完整平台应校验并摄取文件，分配稳定 `artifactId`、
  hash、size 和受控访问句柄。

文件事件实现见
[`web_channel.py:1089`](/home/liujunnan/gs-ai/QwenPaw+cowagent/delivery/offline-install/patch-mounted/frontend/channel/web/web_channel.py:1089)。

## 7. dsh `rc.2` 的能力和限制

### 7.1 可以作为运行时核心的依据

dsh Session 被源码定义为一次 Agent 交互的 append-only source of truth；事件是 lossless JSON，Session 内
`seq` 连续，持久化可以原样保存规范日志。见
[`types.ts:230`](/home/liujunnan/gs-ai/DeepSeek-Harness/packages/core/session/src/types.ts:230)。

dsh 已具备：

- Session append-only event log 和 JSONL/SQLite persistence seam。
- Agent 生命周期、取消和 `whenIdle()`。
- 插件宿主、profile、Storage、Goal、Jobs、Schedule、Workflow、Approval。
- Session 事件实时下行和 API Proxy 基础设施。

因此 dsh 有资格成为执行控制面，而不是只转发 CowAgent 数据。

### 7.2 外部插件事件的持久化限制

`SessionEventMap` 在 TypeScript 类型层允许 declaration merging，但持久化读取使用构建时生成的
`KNOWN_SESSION_EVENT_TYPES`。源码明确写明：仓库外插件事件不在该清单中，运行时注册面尚未提供。见
[`known-event-types.ts:8`](/home/liujunnan/gs-ai/DeepSeek-Harness/packages/core/session/src/known-event-types.ts:8)。

未知且没有 `ignorable: true` 的事件会拒绝会话重建；而工具、记忆、产物和终态等关键事实又不能安全标成
可忽略。因此不能把 CowAgent 私有事件原样塞进 dsh Session，并声称已经获得可靠恢复。

恢复完整平台路线时应二选一或组合使用：

1. 把必要的通用事件提升为 dsh 构建内已登记的 `Execution Event v1`。
2. 在 `digital-employee-runtime` 插件中维护独立、持久的 Run Ledger；dsh Session 只保存能可靠映射的核心事件
   和非权威展示投影。

### 7.3 dsh Jobs、Storage、API 和 WebServer 的边界

- `ctx.jobs` 是进程内合同，默认 local provider 不提供跨进程 durable Run。官方限制见
  [`jobs/README.md:36`](/home/liujunnan/gs-ai/DeepSeek-Harness/packages/jobs/jobs/README.md:36)。
- `ctx.storage` 是 backend/form 注册中心，不自动提供产品业务数据库、多租户或 RBAC。
- dsh Remote 主要是 unary request/response；实时增量、重放和独立实体流需要专门事件协议。
- dsh WebServer 只是 HTTP/upgrade route carrier，不自带 TLS、认证或 origin policy。见
  [`webserver/README.md:19`](/home/liujunnan/gs-ai/DeepSeek-Harness/packages/host/webserver/README.md:19)。

这意味着完整平台中的 dsh 应保持在本机或受控内网边界，不直接作为面向多租户浏览器的公网 API。

## 8. StaffDeck 的客观定位

StaffDeck 已经提供员工、会话、事件、用户和 tenant 等产品模型。当前 `AgentEvent` 按 `tenant_id`、
`session_id`、`event_type` 和 JSON payload 存储，见
[`models.py:1395`](/home/liujunnan/gs-ai/StaffDeck/backend/app/db/models.py:1395)。它的现状足以支撑早期单环境使用，
没有必要在 MVP 阶段先补完整动态租户切换或复杂 RBAC。

但当前 StaffDeck `/api/chat/stream` 仍直接运行自己的 `AgentLoop`，见
[`chat.py:1220`](/home/liujunnan/gs-ai/StaffDeck/backend/app/api/chat.py:1220)。若未来恢复 StaffDeck + dsh 架构，
该执行点必须替换为 dsh client，避免 StaffDeck AgentLoop 与 CowAgent 形成两条业务执行路径。

StaffDeck 在完整平台中的职责应是：

- 员工广场、员工档案和业务任务入口。
- 用户、tenant、产品权限和业务审计。
- dsh 规范事件的查询与实时展示投影。
- A2UI 受控 Catalog、schema/action policy 和 renderer。

StaffDeck 不应拥有 CowAgent 执行终态，也不应被封装成 dsh 插件。

## 9. A2UI、插件和长任务的已得结论

这些能力当前全部暂缓，不进入新 MVP；保留以下结论供恢复时使用：

- “一切皆插件”能让 dsh 承载和组合能力，但插件宿主本身不会自动补齐数字员工产品模型、CowAgent 稳定合同、
  多租户、可靠 Run Ledger 或产物存储。
- A2UI 必须使用受控 Catalog、schema 和 action 校验；禁止执行任意 JSX、JavaScript、CSS 或未审查组件配置。
- A2UI Catalog 和产品交互策略由 StaffDeck/产品层拥有，dsh 只负责传输和运行边界校验，CowAgent 只能产生
  候选描述。
- 长任务只能有一个 Loop owner，不能同时让 LoopX、dsh 原生 Agent、Workflow 或另一套 Harness 提交完成状态。
- LoopX 是 dsh 路线的首选候选，不是已经完成验收的最终实现；仍需通过 `rc.2` 兼容、Provider 接入、恢复和
  独立验证 Gate。
- 自由 swarm 可以作为 CowAgent 一次执行内部的策略，但不能代替平台唯一 Goal/Loop 状态权威。

## 10. 已识别的主要风险

1. CowAgent Web API 是面向其控制台的接口，事件和 Cookie 语义可能随版本变化。
2. CowAgent SSE 是短期内存重放，不是持久审计或恢复日志。
3. `done`、`cancelled`、`stream_end` 不能机械映射成平台终态。
4. CowAgent 文件 URL 和绝对路径不能直接成为产品 Artifact 合同。
5. dsh 仓库外必需 Session Event 当前存在重载兼容限制。
6. dsh Jobs 不是 durable Run registry，WebServer 也不是认证网关。
7. StaffDeck 当前有自己的 AgentLoop；未来接入时必须移除第二执行路径。
8. 浏览器不应直接获得 CowAgent Web 密码、Cookie 或 dsh 内部接口访问权。

## 11. 暂缓范围与恢复条件

当前暂缓：

- StaffDeck 与 dsh 的正式适配。
- `digital-employee-runtime`、`ExecutionProvider v1` 和持久 Run Ledger。
- CowAgent 稳定 shim、终态协议和 Artifact 摄取。
- 多租户、完整 RBAC、业务审计持久化。
- AG-UI、A2UI、受控 Catalog。
- LoopX、长任务、Goal、SOP、Gate、恢复和预算。

未来恢复完整平台路线时，先按以下顺序重新开始：

1. 在主基线中重新确认完整平台阶段目标。
2. 冻结 `Execution API/Event v1`、状态机、三层 ID、取消和 Artifact 合同。
3. 实现并验证 CowAgent Provider/shim，不让 StaffDeck 直接依赖 CowAgent Web 私有事件。
4. 建立 dsh 侧持久 Run Ledger 和可靠事件下行。
5. 再并行进行 StaffDeck 接入、A2UI 和 LoopX Gate。
