# 企业 A2UI 前端组件与专业能力选型

> 资料与版本快照：2026-08-18。本文件回答两个问题：`shadcn/ui` 是否够用，以及为什么最终采用有边界的混合路线。

## 结论

`shadcn/ui` 够做默认 UI 基础，但不应被误解为完整企业能力包。最终采用：

```text
默认源码/视觉层：Tailwind CSS v4 + shadcn/ui
复杂企业能力：Ant Design 6，封装为隔离 adapter
聊天 UX：assistant-ui（需要时）
Agent 动态 UI：CopilotKit + AG-UI + A2UI + 受控 Catalog
```

这不是把两套组件库的 Button、Dialog、Form 混在一起，而是让每一层只负责自己擅长的事：
shadcn 让 AI 直接读写项目源码，AntD 让复杂 Table/Tree/筛选能力不必重造，Catalog 让 Agent 只能使用项目允许的语义组件。

## 为什么 shadcn 是基础层

shadcn 的核心不是“npm 里有多少组件”，而是把组件源码复制进项目，配合 Tailwind、registry、Blocks 和 MCP。这样：

- Agent 能直接阅读实现、props、样式和测试，而不是猜黑盒主题 API。
- 项目能按自己的 tokens、响应式和状态约束修改组件。
- 组件可以在 Storybook 中用项目真实 props 和状态验证。
- 它与 Vercel Chatbot、assistant-ui 等 AI 项目实践有直接的代码和生态连接。

边界也必须承认：shadcn 的 Data Table 文档本身采用 TanStack Table 组合方式，它提供可复制的 UI 和行为基元，
不自动提供所有企业级虚拟滚动、树编辑、批量操作或权限规则。源码可见不等于业务能力已经完成。

## 为什么不是 AntD 全家桶

AntD 的 Table、Tree、Form、DatePicker 和反馈能力很成熟，但把它作为全局主体系会牺牲一部分源码层控制和定制自由；
而且 AI 产品中常见的聊天、工具调用、生成式区域并不等同于普通后台组件。LobeHub 的真实工程规则也是
“headless/base-ui -> 自有 UI -> AntD”分层，而不是所有页面直接使用 AntD。

因此 AntD 的正确位置是“专业能力适配层”，不是“所有组件的默认来源”。

## 混合边界

| 层 | 默认来源 | 项目对外暴露 | 禁止事项 |
| --- | --- | --- | --- |
| 基础 UI | shadcn/ui + Tailwind | `Button`、`Dialog`、`Tabs`、`Input`、`Popover` 等项目组件 | 业务代码直接散落 registry 复制代码 |
| 复杂企业控件 | AntD 6 | `EnterpriseTable`、`EnterpriseTree`、`AdvancedFilters` | 向业务层泄漏 `TableProps` 或 AntD token |
| AI 聊天 | assistant-ui，或 AntD X（若整页已是 AntD） | `AgentThread`、`ToolCallCard`、`ApprovalPrompt` | 同时安装两套全局聊天状态和主题 |
| 动态 UI | BYOC Catalog | `TaskForm`、`ResultTable`、`ApprovalActions` 等语义组件 | Agent 直接传 CSS、任意 JSX、任意第三方 props |
| 图表 | Recharts/Tremor 源码模式；ECharts adapter | `TrendChart`、`KpiChart`、`ComplexChart` | 让 Agent 直接生成任意 chart option |

必须处理的工程边界：AntD CSS layer、reset、token bridge、portal、z-index、SSR/hydration、主题和 bundle。混合不是把 import 写在同一文件就完成。

## 图表、图标、动效、3D 怎么归位

这些是独立专业能力，不再硬塞进“组件库”这个词里：

| 能力 | 默认 | 何时升级 | 证据与限制 |
| --- | --- | --- | --- |
| 普通图表 | shadcn Chart 源码模式 + Recharts | 地图、Sankey、Treemap、热力图、大数据 | Recharts 是 React 组合式 SVG；shadcn 不包死 Recharts API |
| 复杂图表 | ECharts + `echarts-for-react` | 真实出现复杂数据分析需求 | ECharts 支持 20+ 类型、Canvas/SVG、渐进式渲染；需按模块注册 |
| 图标 | Lucide React | 品牌/填充图标缺口时局部 Tabler | Lucide 1600+、tree-shaking、TS；Tabler 6100+ MIT；Iconify 更适合搜索而非公共 API 运行时 |
| 基础动效 | CSS | 需要状态、手势、布局、presence 时 Motion | 优先动画 opacity/transform，尊重 reduced motion |
| 复杂动效 | GSAP | 时间轴、滚动叙事、SVG morph | 成熟但 imperative；只在收益明确时引入 |
| 3D | Three.js + R3F + drei | 产品确实需要 3D 主视觉/场景 | R3F v9 与 React 19 配对；必须 Client-only、懒加载和性能预算 |

## Agent 使用规则

AI 不应该收到“把这个页面做漂亮”这种空指令，而应得到：

```text
项目级组件目录和 import 规则
组件用途、props、默认值和状态矩阵
tokens、响应式和 a11y 约束
Storybook stories 与可复制示例
A2UI Catalog 的 schema、事件白名单和拒绝规则
验收命令：typecheck、测试、浏览器、截图和 axe
```

图标必须从 `icon-library.ts` 的组件对象或受控名称映射中选择；禁止 AI 手写 SVG。图表必须由项目级语义组件接收已校验的数据，
而不是把 ECharts/Recharts 的整个配置面暴露给模型。3D 同理：Agent 只组合预先批准的场景组件，不直接生成任意 WebGL 代码。

## 选型比较

| 路线 | 优点 | 代价 | 本项目结论 |
| --- | --- | --- | --- |
| shadcn/ui + Tailwind | AI 可读源码、定制自由、registry/MCP、适合产品化 UI | 复杂企业行为需组合和维护 | **默认基础层** |
| Ant Design 6 | 企业表单、Table、Tree、反馈完整，中文场景成熟 | 视觉和 API 更重，混合需处理 CSS/SSR | **复杂能力 adapter** |
| MUI Core/X | 全球生态、数据能力强 | X Pro/Premium 许可和 Material 视觉边界 | 不作为默认 |
| PrimeReact/Mantine/Chakra | 各有完整组件覆盖 | 当前 A2UI/AI 协作证据不如前两者集中 | 不作为默认 |

## 不重复造轮子的具体规则

1. 基础 Button/Dialog/Dropdown/Tabs/Input：使用 shadcn 源码组件。
2. 复杂 Table/Tree/筛选：先复用 AntD，包成项目 adapter；只有明确缺口才评估 AG Grid。
3. 普通图表：先复用 Recharts/Tremor 现有模式；复杂图表才用 ECharts。
4. 图标：先查 Lucide，Iconify 只做搜索/补充，不让 AI 重画 SVG。
5. 动效：先 CSS，再 Motion；只有复杂时间轴才 GSAP。
6. 3D：使用 R3F/drei helper；不手写 Three.js boilerplate，且只在需求出现时加载。
7. 每个复用能力都必须提供项目语义 API、状态矩阵、Storybook 和测试，而不是直接把第三方 API 传播到页面。

## 固化结论

```text
默认固定页面       -> shadcn/ui + Tailwind + 项目 tokens
复杂企业控件       -> AntD 6 adapter
聊天 UX            -> assistant-ui（按需；AntD 全局项目才考虑 AntD X）
Agent runtime      -> CopilotKit
Agent 事件         -> AG-UI
Agent 动态 UI      -> A2UI v0.9.1 + 受控 BYOC Catalog
普通图表           -> Recharts/Tremor 源码模式
复杂图表           -> ECharts adapter
图标               -> Lucide；Iconify 仅作检索/补充
动效               -> CSS + Motion；GSAP 按需
3D                 -> Three.js + R3F + drei 按需
```
