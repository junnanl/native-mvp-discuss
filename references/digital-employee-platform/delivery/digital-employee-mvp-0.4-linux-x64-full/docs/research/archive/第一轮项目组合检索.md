## 需求映射

```text
产品前端：dsh 主体 + 自有页面，不限数字员工概念，使用成熟项目参考与 A2UI
短任务：用户 -> dsh -> ExecutionProvider -> 当前 CowAgent
长效任务：dsh -> 唯一 Loop owner -> ExecutionProvider 有界执行 -> 验证/写回 -> 下一轮/停止
```

前端参考项目只用于提炼产品设计，不因 UI 入选就承担 runtime；dsh 负责主体和插件组合；Loop 项目只负责
长效循环；实际执行统一走当前 `ExecutionProvider`。检索职责仍分开，但部署在一个 dsh 主体下收敛。

## 第一轮历史判断

> 本节基于此前“管理台 + 控制层 + runtime 一体组合”的假设，现只保留为候选项目证据，不作为当前结论。

### 1. 没有发现“高 Star、开箱即用、同时覆盖员工市场 + 长效任务 + CowAgent 接入”的单一项目

Dify 的 Star 很高，但它是完整 AI 应用平台；它不是一个可以轻量挂在 CowAgent 上面的数字员工管理壳。
AgentSpace 的产品语义最贴近管理台（本轮 GitHub API 为 949 Star），但 API contract 和 durable execution 证据不足，暂时只能作为管理台参考。

因此，不把“找一个全包项目”作为默认路线。

### 2. 上一轮比较基线：独立 LoopX + CowAgent（已被 dsh 主体路线取代）

LoopX 的官方 README 和 custom runner 文档明确其定位：`local-first`、provider-neutral、状态和目标
保存在本地，支持本地 dashboard、custom runner/worker bridge、goal/todo/claim/gate/quota/evidence/
handoff，并且核心包声明没有标准库之外的运行时依赖。它适合放在 CowAgent 上面做长效控制层。

这里的“可离线”只针对 LoopX 控制层本身。若 CowAgent 仍调用公网模型或外部 SaaS，整套系统仍不算
air-gapped；模型 provider、向量库、数据库、依赖缓存、镜像和遥测开关必须另行验证。

但 LoopX 的外层 runner 仍负责唤醒、启动 Agent、应用 scheduler hint；LoopX 自己不是常驻的中心化
模型调度器，也不是“自动拆目标并同时向多个 CowAgent 发请求”的通用 task queue。多 CowAgent fan-out
需要由 CowAgent 能力、一个轻量 manager，或另一个明确的任务执行平台承担。

该阶段尚未把 dsh 的插件宿主身份纳入比较。后续源码核验已发现 LoopX 官方仓库含真实
`packages/dsh-loopx-plugin`，因此当前改为优先验证 `dsh rc.2 + LoopX 插件 + ExecutionProvider`；
LongHorizon 只保留 MEA/Audit 参考。由于项目是公司内网、低并发，Trigger.dev 仍不进入第一优先级。

```text
dsh-v0.1.1-rc.2（主体、插件、管理入口）
  + LoopX dsh 插件（唯一长效状态 owner）
  + ExecutionProvider -> CowAgent（当前实现，可替换）
  + 自有产品页面 / AG-UI / A2UI / 受控 Catalog
```

这条组合是当前默认验证路径。需要自己写的核心不是 Agent 执行器、通用任务队列或 Loop 状态核，而是：

- `ExecutionProvider`：把当前 CowAgent 的 Manager/Plan/子 Agent 结果包装为 LoopX 可记录的 bounded turn，
  并补齐取消、超时、重试、恢复、回传事件和证据。
- 数字员工领域模型：`Employee`、`Skill`、`SOP`、`Goal`、`Run`、`Gate`、`Evidence`、`Artifact`、`Quota`。
- 管理台页面和权限/审计边界。
- CowAgent 事件到 AG-UI/A2UI 的映射，以及未知事件、重复事件、断线重连和幂等策略。

### 3. LoopX 与 Trigger.dev 的真实关系

之前把“LoopX 控制层足够”直接推导成“Trigger.dev 不需要”，是不准确的；但结合你现在的低并发
内网约束和 CowAgent 已有的会话内 Plan/子 Agent/cron，当前可以有依据地把 Trigger.dev 排除在默认组合之外。
官方文档显示：

| 能力 | LoopX | Trigger.dev |
| --- | --- | --- |
| 目标、Todo、Gate、Evidence、Quota、Handoff | 主责 | 不理解这些 Agent 治理语义 |
| 跨会话目标状态和 peer claim/lease | 主责 | 不是核心模型 |
| 通用任务队列、worker、run 生命周期 | 不是核心 | 主责 |
| 自动 attempt retry/backoff | adapter 需要证明 | 内建 maxAttempts/backoff/jitter |
| 任务级幂等键和 TTL | 需要 adapter/写回策略 | 内建 task idempotency key |
| 并发、队列、按用户/组织限流 | 有 quota/scheduler/lease，但不是通用队列 | 内建 queue/concurrencyKey/pause/resume |
| 持久等待和 HITL token | 有 gate，但不是通用 waitpoint runtime | 内建 wait/forToken，适合审批等待 |
| 实时 run 状态、日志、流订阅 | 有事件 ledger/status 投影 | 内建 realtime run/event stream |
| 中心化拆目标并启动多个 CowAgent | 没有通用 manager | 可以编排多个 task，但仍需 CowAgent adapter 和汇总语义 |

因此，正确判断是“有语义重叠，但能力不等价”。

### 4. 什么时候才需要别的控制层项目

- `Trigger.dev`：当前不纳入默认组合。只有当 CowAgent/自定义 runner 无法满足任务级队列、自动
  retry/backoff、idempotency、持久 wait/HITL、实时 run stream 或明确的多 CowAgent fan-out 时，才作为
  LoopX 下层的备用 task runtime。全离线 self-host 需要 webapp、worker、Postgres、Redis、事件/对象存储
  等多服务，并关闭 telemetry，不能把 Cloud 的 Checkpoints 语义直接假定到 self-host。
- `Temporal`：只有当任务需要严格 durable execution、长时间 timer、Signal、Replay、跨节点高可用
  和强恢复语义时再引入。它是底层内核，不能替代 LoopX 的 goal/gate/evidence 语义。
- `Hatchet`：作为 Temporal/Trigger.dev 的替代候选，不与 LoopX 默认并用。
- `Dify`、`AgentSpace`：更偏管理台/工作区/应用平台，不能因为有“Agent 管理”页面就替代 LoopX；
  全离线时还需检查其数据库、模型服务、插件和遥测依赖。
- `CopilotKit`、`AG-UI`、`A2UI`：仍需要，它们是前端协议/展示层，不是云服务前提；部署时使用本地包和自有 runtime。

### 5. 任务可靠性更高时的替代组合

```text
最新版 CowAgent
  + Temporal（durable execution kernel，自托管）
  + 自建数字员工 control plane / Next.js 管理台
  + AG-UI + A2UI
```

Temporal 更适合跨天、长等待、重放、复杂 Signal 和严格恢复语义，但它不是即插即用的 Agent 平台，工程量明显高于 Trigger.dev。

### 6. 多 CowAgent 并发派发的结论

Trigger.dev、Temporal、Hatchet、AutoGen、CrewAI 和 LangGraph 都能在不同层面表达并发或多 Agent，但“能并发”不等于“能管理数字员工”。
要实现中心化拆解并同时派发多个最新版 CowAgent 会话，至少需要：

```text
Manager/Control plane 拆解目标
  -> 为每个子任务创建独立 run/worker lease
  -> adapter 启动多个 CowAgent 会话
  -> 收集事件、结果、证据和失败状态
  -> 汇总/门控/重试/人工审批
```

Loop 类项目是否已经提供这套中心化 fan-out，当前不能凭名称判断；LoopX 官方文档明确 Turn 是
experimental transaction boundary，不是 permanent scheduler 或 multi-Agent coordinator。必须查
官方仓库的 worker/adapter、并发、持久化和事件文档。若没有，就把它当 loop/evidence 控制层，另外
选择 Trigger.dev/Temporal/Hatchet 或自建轻量 manager 承担 fan-out。

## 暂不采用的项目形态

- [deep-agents-ui](https://github.com/langchain-ai/deep-agents-ui)：前端交互参考价值高，但仓库已 archived，不作为长期上游依赖。
- [Flowise](https://github.com/FlowiseAI/Flowise)：Star 高但检索标记为 archived，且偏可视化工作流，不作为本主线底座。
- `HubOS`、`aranea-agents`、`GoAgent`、`agent-gogo`：概念贴近，但当前 Star/社区/运行证据不足，不满足“高 Star 优先”的筛选条件。
- `agency-agents`：更像角色/流程/交付物模板市场，不是 runtime、管理台或 durable control plane。

## 新范围下的下一轮核验清单

1. 前端参考线：不限于 Multica、StaffDeck 或“数字员工”项目；从 Agent workspace、Mission Control、任务工作台等更广范围核验信息架构、交互、页面结构和技术栈，只评估可借鉴部分，不评估其 runtime 是否替换 CowAgent。
2. CowAgent 接口线：只查最新版公开 CLI/HTTP/SDK、Plan、子 Agent、cron、事件、取消、暂停、恢复和执行证据。
3. Loop 范式线：先定义统一评价协议——Goal/停止条件、外部持久状态、有界执行、独立 Audit、预算、Gate、自动触发和重启恢复。
4. Loop 项目线：目标是收敛一个高 Star、活跃、可离线、能外挂任意 harness/CowAgent、可实际复用的项目；广泛核验 LoopX、MEA/LongHorizon-Harness、Omnigent、Mission Control、声明式 orchestrator 等官方仓库。聊天记录里的项目名称只是线索，未经 canonical repo 和代码证据核验不得进入推荐。
5. 对比必须回答：谁决定下一步、谁调用 CowAgent、谁独立验证、状态真源在哪、如何停止、air-gap 依赖和 CowAgent adapter 工作量。
6. dsh 不再作为“外挂 Loop”候选，而是已冻结的主体平台；DeerFlow、CrewAI 等其他完整 Harness 不进入组合。
   对具体执行 Harness 的替换通过 `ExecutionProvider` 完成，不反向改变主体选型。
7. Trigger.dev 只在低并发方案仍缺通用任务队列、重试/幂等、持久 waitpoint 或 run stream 时复核。
8. 最终用一条真实长效 SOP 做相同 PoC，不按叙事、Star 或项目口号直接决定。
