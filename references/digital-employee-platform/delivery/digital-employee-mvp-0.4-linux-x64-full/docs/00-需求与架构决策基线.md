# 数字员工平台：需求与架构决策基线

> 状态：当前实施基线（SSOT）
>
> 决策日期：2026-08-26
>
> 本文件只记录产品需求、架构边界、当前决策和验证状态。候选项目的完整检索、源码摘录和逐步验收
> 分别放在 `docs/research/`、`docs/02-dsh主体与插件职责矩阵.md` 和 `docs/poc/`，不在这里重复维护。

## 0. 一页结论

本项目是一个面向公司内网的数字员工管理台与员工市场，不是另造一套 Agent Harness。当前组合为：

```text
自有产品前端 / dsh Web slots / A2UI
                  |
dsh-v0.1.1-rc.2（主体平台、插件宿主、管理入口、Loop 控制面）
  ├─ Session / Storage / Goal / Jobs / Schedule / Workflow / Approval
  ├─ dsh-ag-ui / A2UI / taskboard 等已存在能力（按需启用）
  └─ 一个 Loop owner（首选验证 LoopX dsh plugin）
                  |
ExecutionProvider（稳定、可替换的执行兼容层）
                  |
CowAgent（当前唯一实际执行器；未来可替换）
```

核心原则：

> 数字员工是产品表达；dsh 是主体与插件宿主；Loop 负责跨轮控制；`ExecutionProvider` 是可替换边界；CowAgent 负责每一次真正的执行。

需求和架构边界已经冻结；插件在 `dsh rc.2 + air-gap + CowAgent` 组合下是否开箱可用，仍必须通过 PoC 证明，不能把“已有实现”写成“生产完成”。

## 1. 项目目标与范围

### 1.1 产品目标

建设一个企业内部高频使用的交互式 Web 工作台，统一呈现：

- 数字员工市场、员工档案、能力和 Skills；
- 短任务对话、Plan、工具/子 Agent 过程、结果和产物；
- 长效目标、SOP、轮次、Trace、证据、审批、人工接管和恢复；
- 基础用量、运行环境、离线健康、权限和审计。

数字员工是岗位、能力、SOP 和权限的产品模型，不是一个新的执行 runtime。前端参考可以来自数字员工、Agent workspace、Mission Control、任务工作台或可观测性产品，不按项目名称设限。

### 1.2 非目标

- 不从零重写 Agent Harness、通用任务队列、A2UI renderer、任务台账或插件市场。
- 不让 dsh 原生 Agent 和 CowAgent 同时成为业务执行器。
- 不把任何前端参考项目整仓 fork 成第二个平台。
- 不以高并发 worker fleet、云端 SaaS 或公网部署为当前目标。

## 2. 需求基线（R）

| R3 | CowAgent 使用最新版，但未来可能更换 | 领域层只依赖 `ExecutionProvider`；更换 Harness 只新增实现，不改产品、Loop 或前端 | 已冻结 |
| R4 | 数字员工主要是产品概念和前端表达 | `Employee / Skill / SOP / Goal / Run / Evidence` 是产品领域模型，不承担执行 | 已冻结 |
| R5 | 前端参考不局限于数字员工项目 | 采用组合参考：Multica、Mission Control、LobeHub、Langfuse、StaffDeck/AgentSpace、Dify、Open WebUI 等；只借信息架构和交互 | 阶段性确定 |

| R7 | 需要可复用的 Loop 工程范式 | dsh 主体下优先验证 LoopX dsh plugin；LongHorizon 只作 Manager/Executor/Auditor 参考，Symphony 只作 runner 参考 | 首选候选，待 Gate |
| R8 | 支持跨会话、跨天长效推进 | 必须持久化 Goal/State、轮次、停止条件、证据、Gate、预算，并支持重启恢复 | 协议已定，运行待验 |
| R9 | dsh 作为主体并控制 Loop | dsh 做平台骨架、插件宿主、管理入口和控制面；不把 dsh 原生 Agent 当作 CowAgent 替代品 | 已冻结边界，接入待验 |
| R10 | Developer Preview 和未来破坏性变更不阻塞 | 锁定官方 `dsh-v0.1.1-rc.2` tag、commit、profile、依赖和离线制品 | 已冻结 |
| R11 | 全套离线、公司内网、低并发 | 运行时不依赖公网、云模型、在线市场、托管服务或外部遥测；不建设通用 worker fleet | 硬约束 |

## 3. 产品流程与领域边界

### 3.1 三条主流程

```text
产品前端：员工市场/档案 -> 创建任务或 Goal -> Run/Trace -> 审批与产物

短任务：用户 -> dsh/自有前端 -> ExecutionProvider -> CowAgent -> 事件/结果 -> 前端

长效任务：用户或 SOP -> dsh Goal -> 唯一 Loop owner
  -> 读取持久状态并决定一个 bounded next step
  -> ExecutionProvider 调用 CowAgent
  -> 机器校验/独立 Audit -> 写回证据
  -> 停止、人工 Gate、重试或下一轮唤醒
```

### 3.2 领域对象

产品层至少需要 `Employee`、`Skill`、`SOP`、`Goal`、`Run`、`Round`、`Gate`、`Evidence`、`Artifact` 和 `Quota`。这些对象映射到 dsh/LoopX 的 ID，但不直接暴露 CowAgent 私有类型。

### 3.3 状态真源

- dsh Session/Storage：会话事件、基础持久化和平台投影。
- LoopX ledger（或经验证的唯一 Loop 实现）：跨轮 Goal、claim、预算、证据和下一次唤醒。
- `ExecutionProvider`：一次 run 的执行事件和终态适配。
- 前端：只保存页面交互状态和服务端数据缓存，不自行创造第二份任务完成状态。

同一业务 run 只能有一个 Loop 状态权威和一个实际 `ExecutionProvider`。对话 transcript 是观测材料，不是跨轮状态真源。

## 4. 架构决策（D）

### D1. 主体平台

冻结官方 `dsh-v0.1.1-rc.2`，commit `b150a551b8d465e31e418e1b2eaf5e79bbb7d28e`。直接复用 Session、Storage、Goal、Jobs、Schedule、Workflow、Approval、profile、plugin、Web slots 和现有事件基础设施。

### D2. 唯一执行边界

```text
dsh / LoopX
  -> ExecutionProvider.start(request)
  -> CowAgent bounded turn
  -> normalized events / evidence
  -> terminal result
  -> validator / Auditor
  -> durable writeback
```

`ExecutionProvider` 至少需要表达 `start`、按序 `events`、`inspect` 和 `cancel`；`resume`、超时、权限和幂等语义由项目契约和适配器补齐。公开 CowAgent API 未证明前，不逆向 Web 私有接口。

### D3. Loop owner

运行时只允许一个 Loop owner。首个实现候选是 LoopX 的 dsh 插件：先验证 `rc.2` 兼容，再把 Driver 的默认 dsh Agent 执行点改接 `ExecutionProvider`。LongHorizon、Symphony、Trigger.dev 不与 LoopX 并列成为状态源。

### D4. 前端宿主与 A2UI

- dsh client/Web slots 优先承载产品入口；只有独立管理页面超出 dsh shell 能力时，才增加独立 Next.js 应用。
- 固定页面使用 React + Tailwind/shadcn；复杂企业控件通过隔离的 AntD adapter。
- Agent 事件使用 AG-UI（默认 SSE）；动态 UI 使用 A2UI 和项目受控 Catalog。
- 当前原型已验证 CopilotKit A2UI renderer；dsh 集成候选为 Valuz A2UI 插件。两者不能在同一 surface 同时拥有 renderer、会话或状态控制权，最终以 dsh smoke 结果确定。

### D5. 复用与自研边界

| 能力 | 优先复用 | 本项目只负责 |
| --- | --- | --- |
| 平台骨架 | dsh 原生 Session/Goal/Jobs/Schedule/Workflow/Approval/Storage | 领域投影和配置 |
| Loop | LoopX dsh plugin | `rc.2` 兼容和 Provider seam |
| 事件与动态 UI | `dsh-ag-ui`、A2UI renderer、受控 Catalog | 事件映射、白名单和主题 |
| 看板与台账 | taskboard/task-center | 替换其直接 `ctx.agents` 执行调用 |
| 审核 | auto-review、dsh Approval | 角色、权限和结果映射 |
| 产品页面 | 借鉴成熟项目 | Employee/SOP/Run/Trace 页面和交互 |
| 离线供应链 | 内网制品库、固定 tarball、镜像和 lockfile | SBOM、许可证、网络审计和配置 |

真正需要自研的是薄的 `ExecutionProvider`/CowAgent adapter、插件执行边界适配、产品领域投影和离线制品配置，不是另一套平台。

## 5. 产品前端与技术方案摘要

### 5.1 页面信息架构

一级入口围绕用户任务收敛：员工市场、我的任务/Goals、运行与 Trace、SOP/模板、审批/Gate、设置与离线健康。员工详情、任务、Run 和 Trace 通过页内 Tab 或上下文抽屉关联，避免重复建模。

参考职责：

| 页面能力 | 主要参考 |
| --- | --- |
| 员工市场、档案、能力和团队 | Multica、StaffDeck、AgentSpace |
| 运营总览、审核、系统状态 | Mission Control |
| 任务、Agent 交互和产物 | LobeHub、Open WebUI |
| Trace、Observation 和评估 | Langfuse |
| SOP、人工输入和运行监控 | Dify |

### 5.2 默认前端栈

```text
React + TypeScript strict
Tailwind CSS v4 + shadcn/ui（默认源码层）
Ant Design 6（复杂 Table/Tree/筛选的隔离 adapter）
CopilotKit + AG-UI + A2UI + 受控 Catalog
TanStack Query + React Hook Form + Zod 3
Vitest/RTL + Storybook + Playwright + axe
```

图表、图标、动效和 3D 均按真实缺口按需接入；不预装多个完整设计系统，不让第三方 API 泄漏到业务层。详细版本和复核条件见 [`01-技术栈与前端方案.md`](./01-技术栈与前端方案.md)。

### 5.3 A2UI 安全边界

Agent 只能产生经过 schema 校验的组件描述和 action。Catalog 负责组件白名单、props schema、事件路由、大小限制和敏感字段过滤；未知组件或非法字段必须拒绝。A2UI action 必须经过 runtime 回传 Agent，并由后续事件或结果证明闭环。

## 6. 长效 Loop 合同

每轮至少持久化：`goalId`、`roundId`、原始目标、输入快照、停止条件、预算、Provider `runId`、最后事件序号、validator/Audit 结果、证据引用、外部 effect key、下一次唤醒时间和状态版本。

统一评价标准：

1. 支持定时、事件或心跳唤醒。
2. Goal、完成标准、最大轮次/时间/预算可持久化并尽量机器检查。
3. 进程重启或换会话后可以从文件/数据库恢复。
4. 明确谁决定下一步、谁拥有认领/租约和冲突处理。
5. 每轮只调用当前 Provider 的一个有界执行。
6. 结果必须经过确定性 validator 或独立只读 Auditor，不能只接受 CowAgent 自报完成。
7. 状态、证据、重试和外部副作用具有唯一事实源；重复唤醒不重复危险动作。
8. 缺少输入、高风险操作或验收失败时进入人工 Gate，并支持处理后继续。
9. 能观察当前状态、历史轮次、证据、阻塞、预算和下一步。
10. 所有运行依赖、许可证、遥测和升级方式可在 air-gapped 环境核验。

## 7. 离线与部署约束

- 管理台、dsh 控制层、事件/任务存储、调度和模型/Agent 服务均在本地或内网运行。
- 不依赖 npm/GitHub/CDN、在线插件市场、云端模型、Copilot Cloud、Trigger.dev Cloud 或外部遥测。
- 联网构建区保存精确 tarball、lockfile、SHA-256、许可证/SBOM 和容器镜像，再导入内网制品库。
- 第一 PoC 使用 `systemd` 保持 dsh profile 存活；systemd 不拥有业务完成状态，也不创建第二套 timer。
- 低并发不等于忽略取消、恢复、幂等和审计；只是暂不引入通用 worker fleet。

## 8. 验证状态（G）

Gate 顺序统一为：

1. **G0 插件兼容**：LoopX、`dsh-ag-ui`、Valuz A2UI、选定 taskboard 在 dsh `rc.2` 的 artifact/profile/runtime/browser smoke。
2. **G1 Provider**：公开 CowAgent 接入面能够完成 `start -> runId -> ordered events -> terminal result`，并证明 inspect/cancel/timeout/resume/idempotency/permission 语义。
3. **G2 SOP 闭环**：`Goal -> bounded turn -> validator/Audit -> evidence -> next/stop`。
4. **G3 恢复与离线**：断网、重启、重复唤醒、人工 Gate、外部 effect readback 和依赖闭包。
5. **G4 前端闭环**：员工详情 -> 创建任务/Goal -> Run/Trace -> Gate -> 恢复 -> verified 完成或明确失败。

当前已完成的是调研、边界收敛和本地前端 runtime spike；G0-G4 的真实组合验证尚未全部通过。详细合同和 fixture 见 [`poc/ExecutionProvider与LoopX验收Gate.md`](./poc/ExecutionProvider与LoopX验收Gate.md)。

## 9. 待确认事实与复核条件

这些是工程验证项，不是重新摇摆的产品需求：

- CowAgent 最新版对外的稳定 CLI/HTTP/SDK/事件/回调接口，以及取消、暂停、恢复、权限和证据能力。
- LoopX 插件能否在 `dsh rc.2` 通过真实 smoke，并把 bounded turn 接到 Provider。
- 机器停止条件、确定性 validator 和 CowAgent Auditor 的分工。
- 登录、组织/租户、角色权限、审计与数据合规要求。
- 单机、Docker Compose、Kubernetes 或隔离内网的最终部署边界。
- A2UI 是先动态填充固定组件，还是进一步让 Agent 在受控 Catalog 内决定组件树。
- 是否存在品牌设计系统、真实 Figma、移动端、Safari/旧浏览器或国际化要求。

若 CowAgent 没有公开稳定 Runtime contract，停止逆向私有接口，使用 Mock Provider 继续验证平台；若 LoopX 核心 binding/writeback 在 `rc.2` 失败，维护最小兼容 fork，或退回 dsh 原生 Goal 做窄范围 PoC。

Trigger.dev 只有在持久 waitpoint、任务级 retry/backoff/idempotency、可靠 fan-out/fan-in、实时 run stream 或多 worker 成为真实缺口时才启动 self-host PoC，并重新核验 Postgres、Redis、遥测和离线升级成本。它不能取得 Goal/Audit 业务真相的所有权。
