On the failure modes of LLM-generated frontend code

A pattern catalogue from two hundred reviewed pull requests, written for engineers who already know the LLM ships working code most of the time, and want a clearer picture of when and how it doesn't.

The audit#

Two hundred merged or rejected pull requests across three production codebases — a SaaS dashboard, a content publishing system, and a developer-tooling site — were reviewed for design and code defects attributable to the LLM that authored or co-authored them.

LLMs ship working frontend code most of the time. The failures, when they happen, are not random. They cluster into recognisable patterns rooted in three things: training-data bias toward popular but mediocre examples, the absence of taste as a constraint during generation, and a subtle gap between syntactic correctness and design intent. This catalogue documents the seven most common failure modes, with examples drawn from a corpus of two hundred reviewed pull requests across three production codebases.

The defect rate by lines-of-code-changed was lower than expected — roughly one design or accessibility defect per three hundred lines, rather than the one-per-fifty that anecdote suggests. What inflates the perceived defect rate is that the failures cluster on the surfaces that matter most: marketing pages, empty states, dashboards, and onboarding flows. [1] The places where a thoughtful designer would have spent the most time are exactly where the model defaults most aggressively to its training median.

1 The corpus excludes purely back-end PRs and PRs where the model only generated tests. Front-of-house surfaces, where design density is highest, are over-represented by design.

Method#

Each PR was scored on five axes — correctness, accessibility, design coherence, code-base fit, and copy quality — by two human reviewers blind to whether the author was a model or a junior engineer. Defects were tagged by category and surfaced into a shared sheet. The result is a frequency table, not an indictment.

The corpus mixes JavaScript (60%) and TypeScript (40%) PRs. The frequencies above are stable across both, with one exception: hallucinated APIs are roughly twice as common in JS than in TS, which suggests the typecheck-and-build mitigation is doing real work.

Seven failure modes#

Each pattern below has a recognisable shape, a plausible cause in the model's training distribution, and a specific test you can apply during review to catch it without reading every line.

1 · The card-grid reflex#

The most common failure. Asked to display a list of three or more conceptually similar items — features, plans, team members, recent activity — the model reaches almost reflexively for an evenly-spaced grid of cards, each with an icon, a heading, and a paragraph of body text. The grid is correct in the sense that nothing is broken; it is wrong in the sense that the pattern was already a cliché in 2018, and using it now signals an absence of editorial judgement.

Note

The fix is rarely "use a different layout." It is "ask whether these items are actually parallel." Three pricing plans really are parallel and a card grid is fine. Three features at the top of a marketing page almost never are; one is the headline, one is supporting evidence, one is a footnote, and they should look like it.

2 · Tailwind-prose syndrome#

When asked to render Markdown content — blog posts, documentation, agent reports — the model defaults to @tailwindcss/typography's prose class with no overrides. The result is a sans-serif body in a system stack, default Tailwind link blue, default code-block grey, default heading scale. It is the most legible bad design ever made and it appears in roughly a third of long-form-content PRs in the corpus.

The fix is not to abandon prose; it is to use it as Tailwind intends, by overriding the type stack, link colour, code-block treatment, and at minimum the H2/H3 hierarchy. [2]

2 A surprising number of mature design systems use prose with only colour overrides and inherit the rest of Tailwind's defaults. The result is recognisable from across the room.

3 · Side-stripe accents#

A tinted vertical bar two to four pixels wide on the left edge of a card, callout, or alert, in the brand or semantic colour. Bootstrap codified this in 2013; it has been a tell of unconfident design ever since. The model produces it especially in admin dashboards and notification components, presumably because the open-source ecosystem is dense with examples.

There is no UI problem solved by a four-pixel coloured stripe that is not solved more elegantly by a small all-caps label or by nothing at all.

Replace it with one of: a small uppercase label in the accent colour above the body; a faint full-bleed tint of the surface; a leading number or icon; or, most often, nothing — the content alone, with surrounding whitespace as the boundary.

4 · Glassmorphism by default#

Frosted-glass surfaces with backdrop blur on every overlay, modal, dropdown, and floating navigation bar. The pattern is correct in roughly one product in twenty — usually a media-rich app where the blurred background is part of the experience. Elsewhere it is decorative noise, costs measurable rendering performance on mid-range hardware, and degrades contrast unpredictably under arbitrary content.

The accessibility regression here is silent. Backdrop-blurred surfaces over photographs routinely fail 4.5:1 text contrast at small sizes; automated audits pass because they sample the surface colour token, not the actual rendered pixels.

5 · The hero-metric template#

Big number, small label below, three supporting stats arranged in a row, gradient accent somewhere. The SaaS landing-page cliché. The model produces it on request for marketing surfaces, on dashboards when the prompt is "show me the key metrics", and occasionally inside cards in admin tools. It looks identical across every category — a fintech, a mental-health app, a developer tool, an e-commerce site — which is precisely why it has stopped working.

6 · Modal as first thought#

Asked to add a confirmation, a settings panel, an item editor, or a multi-step input, the model reaches for a modal more than half the time, even when the surrounding UI is clearly a multi-pane application that could host the same affordance inline. Modals interrupt; they are the last resort and the model treats them as the first.

A reviewer-friendly heuristic: if the action is reversible and the user is likely to take it more than once and the surrounding UI has any vertical real estate, the modal is wrong. Inline expansion, a side panel, a toast with an undo, or a dedicated route are all better defaults.

7 · Hallucinated APIs#

Lower frequency, higher severity. The model imports a hook, prop, or method that does not exist in the version of the library actually installed. The patterns it invents are almost always plausible — they read as if they should exist — which is exactly why they slip past review until the build fails or, worse, until a runtime error in a code path that wasn't exercised locally.

src/components/Pagination.tsx
tsx 
// Generated. Looks fine. Doesn't compile against react-router 6.4.
import { usePagination } from 'react-router-dom';
//      ^^^^^^^^^^^^^ this hook does not exist in any release.

export function Pagination({ total, perPage }) {
  const { page, setPage } = usePagination({ total, perPage });
  return (
    <nav>
      <button onClick={() => setPage(page - 1)}>Prev</button>
      <button onClick={() => setPage(page + 1)}>Next</button>
    </nav>
  );
}

The defect is invisible in code review because the import looks indistinguishable from a real one; humans pattern-match on whether names are plausible, not whether they exist. Two of the three teams in the corpus had at least one such defect reach main.

Insight

The most reliable mitigation isn't smarter prompting. It's the boring one: a typecheck and a build step on every PR, plus a CI gate that fails on unresolved imports. The model produces hallucinations at roughly the same rate regardless of prompt; what changes the outcome is whether the test catches it.

Cross-cutting causes#

Three forces shape almost every defect in the catalogue. None of them is the model "getting it wrong" in the naïve sense; each is a faithful response to its inputs.

Training-data median

The model has read every Bootstrap demo, every Tailwind UI marketing page, every Dribbble dashboard mockup, every "best practices" Medium article. The plurality vote of that corpus is what it returns when nothing in the prompt pulls it elsewhere. The card-grid, the side-stripe, the hero-metric, the modal — all are statistically correct for the surface they appear on. They are also, increasingly, the visual signature of AI authorship.

Absence of taste as a constraint

Code can be tested for correctness; design cannot. The model has no equivalent of tsc or eslint for "is this fresh", "is this confident", "does this match the brand". Without an explicit anti-reference list in the prompt, it has no incentive to deviate from the training median, and no signal that doing so would be rewarded.

The plausibility–existence gap

Hallucinated APIs survive review because reviewers — human and automated — pattern-match on plausibility, not existence. The model is, in one sense, doing the same thing in reverse: it generates names it expects to find, and the tools we have for catching it are weaker than the ones we use for code that looks wrong.

What works#

Five interventions, in roughly increasing order of effort, that materially reduce the failure rate in the corpus. None require fine-tuning, plugins, or a new framework.

  1. Anti-reference lists in the prompt. The single highest-leverage move. Listing what the model should not produce — "no card grids, no side-stripe accents, no hero metrics" — reduces those defects by 60–80% in re-runs of the same task.
  2. Reference-driven prompts. Naming two or three specific products the design should resemble, rather than adjectives like "modern" or "clean", concentrates the output away from the training median.
  3. Build a typecheck and unresolved-import gate. Catches hallucinated APIs at the lowest possible cost. This is purely tooling work and pays back within weeks.
  4. Review against a defect catalogue. Train reviewers (human or model) to look specifically for the seven failures above, instead of a freeform critique. Defects-found-per-review-hour roughly doubles in the corpus.
  5. Maintain a project DESIGN.md. A page that documents the project's actual visual choices — fonts, palette, spacing scale, callout treatment — gives the model a strong, project-specific anchor that beats every generic prompt nudge in the data.
Lowest cost
Anti-references in the prompt. Five minutes of work, reduces defects in the next response.
Highest leverage
Project DESIGN.md. Compounds across every future task; pays back the day it exists.
Doesn't work
Asking the model to "be more original". The model interprets originality as more decoration; the result is worse, not better.

Treat the anti-reference list and the project DESIGN.md as a reusable preamble for every prompt that touches the UI. Five lines at the top of the prompt produce a step-change in output quality, and the same five lines work for the next ten tasks without modification.

Do not deploy un-typechecked LLM code to a non-trivial project. The hallucinated-API failure mode is rare per PR but high-severity, and it is the one defect class that cannot be reliably caught by review alone. A CI step that fails on unresolved imports is non-negotiable.

Open questions#

Things this report doesn't answer that would be worth a follow-up.

  • How much of the failure rate is explained by model version, and how much by prompting practice? The corpus mixes both, and the variance is wider than expected.
  • Does the same catalogue apply to mobile-first work, or do the failure modes shift? [3]
  • What's the half-life of an anti-reference list before training-data drift overtakes it? The terracotta accent in this very report was a contrarian choice in 2024 and is rapidly becoming a cliché.
3 Anecdotally yes — the mobile catalogue is shorter but the defects are more severe (touch targets, scroll traps).

Glossary#

Card grid
A layout pattern in which conceptually similar items are presented as evenly-sized rectangular containers in a regular grid. Often correct, but the default for any list with three or more elements; the absence of editorial weight is the failure.
Prose syndrome
A specific failure mode of @tailwindcss/typography's default styling, in which Markdown content is rendered with the plugin's defaults — system sans, default scale, default link colour — without project-level overrides.
Glassmorphism
A surface treatment using semi-transparent backgrounds with a backdrop-filter blur. Effective in narrow contexts (media-rich apps) and decorative everywhere else.
Anti-reference
A specific named pattern, product, or aesthetic that a design should not resemble. Stronger than a positive reference for steering generative output, because it removes a region of the output distribution rather than nudging toward one.
