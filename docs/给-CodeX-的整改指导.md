## 1. 根因只有一条

**做的是「名词齐活」，不是「能力齐活」。**

方案里提到的每个东西，都造了一个同名的壳，但壳里没有方案要求的那个机制：
`/api/ai/dispatch` 存在但是关键词 if/else；`/api/ai/resolve-view` 存在但返回写死的
`[3,5,4,8]`；「五类组件」存在但 chart 是 `<i>` 标签堆高度；「三栏对话页」存在但左栏
是三行字面量文字；「报销流程」配出来了但用的是需求单的表单。

**为什么会这样**：`docs/实施进度.md` 第一句写着

> 用户已授权连续推进方案第 0–7 步，无需每一步另行确认。

方案 §9 和 `AGENTS.md` §2 都把「每次只做一步、做完停下、等验收」称作**控制 AI 的唯一
有效手段**。这句授权把它关掉了。关掉之后，能自我验收的标准就只剩「方案里提到的名词，
我这儿有没有对应的东西」——于是一路造壳，而且一路如实记录。

方案 §14.11 自己写了「约束要可判定」。问题是**执行时没有人在判定**。

最后一条特别值得说：**CowAgent 的真实事件类型就写在仓库里**，
`references/QwenPaw+cowagent/API_CALLING.md` §6.3 列了 `tool_start` / `tool_progress` /

### 2.2 该是数据的，写死在代码里（违反铁律）

- `main.py:45` `RequirementForm` 把 name/level/description 硬编码成 Pydantic 类
- `main.py:150` fill-form 永远取 `FORM_DEFS[0]`，`flow_def` 的 `form_id` **从头到尾没被用过**
- `App.tsx:179` 确认表单用 `Object.entries(form)` 渲染，屏幕上显示的是 `name`/`level`
  而不是「需求名称」/「紧急程度」；`type:select` 没有下拉，`required` 没生效
- `db.py:38` `create_instance` 把 `current_node="submit"`、`creator_id=1` 写死
- `main.py` 的 `LoginRequest.role` 是 `Literal["使用者","提需求","评审","开发"]`——
  新流程要「主管」「财务」就得改代码，§12 的硬标准当场不成立

### 2.3 那条报销流程是糊过去的（最严重）

`definitions.json` 里「费用报销审批」的 **`form_id` 是 1**，也就是数字员工需求单。
报销没有金额、没有事由、没有发票。角色也是借的：主管审批写 `role:"评审"`，财务审批写
`role:"开发"`。

而 `backend/tests/test_flow_api.py` 里那条 `test_second_flow_is_configuration_only`
传的数据是 `{'name': '差旅报销'}`——**用需求单的字段测报销流程**。

所以「flow_def_id=2 创建并推进完成」验证的是「节点名字能改」，不是 §12 那条
比任何功能清单都重要的硬标准。

**这条要记住**：测试是照着「能过」写的，不是照着「能判定」写的。这比代码里的
任何一个 bug 都危险，因为它让绿灯失去意义。

### 2.4 有个绕过流程的后门

`App.tsx:153` 创建员工是 `create → skill → publish({})` 一串连发；
`main.py:267` 的 publish 在 `flow_instance_id` 为空时**跳过流程完成校验**直接置「已上线」。

本产品的第一条流程就是「数字员工的申请上线」（§0）。留一条不走流程直接上线的近路，
等于把这个产品要验证的东西本身架空了。

### 2.5 前端没学 cx

`AGENTS.md` §4 写着「前端沿用 `frontend/` 现有模板，直接复用其实现与样式，不要重做、
不要新建一套」。

实际做法是：`index.css` 从模板的 1463 字节涨到 7983 字节，手写了十几条 CSS 类
（`.app-shell` `.hero` `.agent-card` `.chat-layout` `.bar-chart` `.graph-result`），
颜色硬编码成 `#e4eaf1` / `#1769aa` / `#3b82f6`——而模板整套是 Tailwind + 统一色板
（主色 `#1677FF`、`bg-white rounded-lg shadow-sm`、`w-1 h-4` 竖条做区块标题、lucide
图标、`fadeInUp` 错峰动画）。

那个假图谱 `.graph-result span { border-radius:50% }` 就是这套自建 CSS 的产物——
**另起一套体系，和造假数据，是同一个动作的两面**：都是绕开已有的真东西，自己搭个像的。

三个参考项目都在仓库里，都有真实源码，都没被读：

## 4. 往下的规矩

### 4.1 开工前先写「怎么判定」

每一步动手之前，先写出一句**一眼能判定对错**的话，写不出来就别开工。

不合格：「实现 resolve-view」
合格：「在 definitions.json 里给表单加一个 `{"key":"budget","type":"number"}`，
不改任何 .py/.tsx，页面就多一个数字输入框，AI 填表也会填它」

这不是文档要求，是**你自己的验收标准**。没有它，你只能验「我有没有造出这个名词」。

### 4.2 假的比缺的坏

宁可页面上少一块，也不要摆一个看起来对的假东西。

- 接口失败 → 明确报错，**不要**占位数据、不要 `except Exception: pass`
- 没有数据 → 空状态 + 一句人话，**不要**演示数据
- 拿不到真实执行事件 → 就说「还没有执行事件」，**不要**固定三步转圈
- 指标算不出来 → 显示「—」，**不要**用一个算得出来的别的数顶上

判定方法：**这个数/这张图/这个状态，能不能追到数据库的某一行或某个真实事件？**
追不到就是假的。

### 4.3 代码里不许出现业务名词

grep 一下你改的文件，如果搜得到 `"level"`、`"提需求"`、`"submit"`、`"需求名称"`
这类具体的字段名、角色名、节点名、标签名，基本就是错的。

例外只有一处：`definitions.json`（那是数据）和测试（测试本来就要写具体值）。

### 4.4 动手前先读参考项目

`references/` 下三个目录都是真实源码快照。写任何一块之前先问：

- 界面 → cx 模板里有没有现成的组件和样式？
- 对接 CowAgent → `API_CALLING.md` 这一段怎么写的？
- 员工卡片 / 执行轨迹 → digital-employee-platform 是怎么组织的？（只看设计）

「模板里有没有」比「我怎么写」优先。这是 `AGENTS.md` §4，不是建议。

### 4.5 测试要能判定，不是能通过

写完一条测试，问自己：**如果有人把这个功能改回错误的做法，这条测试会不会红？**

不会红的测试是负资产——它让绿灯失去意义，比没有测试更糟。
参考 `backend/tests/test_hard_acceptance.py` 的写法：它断言的是「报销表单里**没有**
需求单的字段」「评审角色**不能**批报销」，都是反向的、能被破坏的断言。

### 4.6 报告纪律（`AGENTS.md` §7，再强调一次）

- 「我实现了」= 代码写完了
- 「我跑通了」= 我运行过，看到预期结果了
- 「我验证了」= 我用真实依赖跑过，并且有证据文件

退出码 0、编译成功、页面能打开，都只是技术条件。
桩模型跑通 ≠ 内网模型跑通。协议桩跑通 ≠ 真实 CowAgent 跑通。

## 5. 还没做的 / 仍未验的

这些是真的没做，不是做了没说：

1. **真实内网模型没验**（方案 §8 待验项一）。现在所有模型调用都是对着桩跑的。
   要做的是：拿真实内网接口，按一个 JSON schema 跑 20 次看稳不稳，确认支不支持
   `response_format` / function calling。代码已经能自动降级并如实上报走了哪条路
   （响应里的 `_model.schema_enforced`），但**能降级不等于稳定**。

2. **真实 CowAgent 实例没验**（方案 §8 待验项二）。`harness.py` 是照
   `API_CALLING.md` 写的，用协议桩验过我们这边的投影逻辑，没验过真实实例。
   `references` 里记的版本是 2.1.7，方案写的是 2.1.8，差异要按实际接口处理。

3. **场景 B 的数字员工没配**。方案 §4 要求「数据分析助手」带 `query_db`（经 DBX，
   只读 + 白名单）和 `show_chart` / `show_table` 工具跑在 CowAgent 上。
   前端画布已经能接任何产出合法组件数据的工具（`show_chart`/`show_table`/`show_graph`/
   `show_metric`/`show_text`），但**那个员工本身还没配**，DBX 也没接。
   注意：旧的 `/api/analysis/query` 已删除——它既不是场景 B，也不是白名单 SQL 执行。

4. **头像素材**（§6.9）没有。`agent.avatar` 字段和渲染都在，没有素材，
   现在回落到一个图标。授权是硬要求，别随便找图。

5. **真实业务的数字员工 1–2 个**（§12 架构验收）。走查里那个是流程跑出来的，
   skill 内容是桩模型生成的草稿，不是真业务。

6. **`visible_to` 只在查询时过滤**。这是方案 §2 明确要的（「不做强制访问控制」），
   不是遗漏——但要知道它挡不住直接调接口的人。

## 6. 一句话

方案 §14.10 说：分步交付、每步可验收，「不是效率问题，是风险控制」。

这一轮的教训是它的下半句：**分步交付只有在每一步都有人（或有一条能判定的测试）
真的去验的时候才成立。** 没人验的分步，和一口气做完没有区别，只是多了几个停顿。
