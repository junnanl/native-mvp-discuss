日期：2026-09-13　　版本：v5.1，取代此前所有版本
性质：**给开发用**。决定项均已与需求方确认；标「待验」的是开工前要验的技术事实，标「待定」的是还没问到的。

## 0. 一页看懂

**做什么**：一个所有人共用的 Web 页面，跑「提需求 → 评审 → 开发 → 上线 → 使用」，第一条流程是"数字员工"的申请上线。

**真正要验证的**：这套做法能不能**快速复制出各种各样的流程**。数字员工只是第一块试验田。

**硬性验收标准**（比任何功能清单都重要）：

> 第一条流程跑通后，配出第二条完全不同的流程（例如报销审批），**不改代码、一天内配完并跑通**。
> 做不到，说明第一条流程的架构白做了。

**技术栈**：前端 React 18 + Vite + TS + Tailwind + react-router-dom + Zustand（沿用现有模板）+ **ECharts**｜后端 Python + FastAPI + Pydantic｜执行层 CowAgent｜数据库用现成的。

**AI 分两种用法**：**场景 A**——路由 / 填表单 / 挑组件出查询 / 生成 SKILL.md 草稿，都是一次模型调用，走模型 API 直连；**场景 B**——探索式分析（查库、出图、多轮追问），走 CowAgent，形态是「数据分析助手」这个数字员工。

**界面定位**：数字员工是主体、占首屏主位，流程管理是配套；取消侧边导航栏，导航由内容本身承担。

**不做**：生成式 UI、多租户、API 管理系统、审计/版本/回滚、权限声明、条件路由、离线交付包。

## 1. 架构

```
┌─────────────────────────────────────────────────────┐
│   业务后端 + 前端（唯一入口，所有人同一个页面）          │
│   登录·角色 │ 流程 │ 表单 │ 数字员工列表 │ 聊天框      │
│   ← 业务逻辑、流程状态、数据 全在这层                  │
│     （其中一个功能是代理数字员工对话，不是"转发层"）      │
└────────┬──────────────────────────┬─────────────────┘
         │                          │
  ┌──────▼───────┐          ┌───────▼──────────┐
  │  模型 API     │          │   CowAgent       │
  │  一次调用      │          │  数字员工运行时    │
  │  无 agent loop│          │  窄接口：装skill/ │
  │              │          │  转发对话/查状态   │
  └───────────────┘          └──────────────────┘
```

**两条线必须分开**：填表和挑组件是一次模型调用就够，不要塞给 CowAgent；数字员工干活要工具和多轮，才走 CowAgent。

**中间这层是主体，不是转发层。** 业务逻辑、流程状态、表单定义、可见范围、三个 AI 调用点全在这儿；代理 CowAgent 对话只是它很小的一个功能。

**管理层与 CowAgent 之间只有四个动作**：装 skill、转发对话、查状态、启停。接口越窄，换执行层代价越小——这是"能复用展开"的物理基础。

## 2. 数据模型

**整份文档最重要的部分。** 变化的东西（表单字段、流程节点）全部是**数据**，不是代码——这就是"架构上考虑到变化"的全部含义。

| 表 | 字段 |
| --- | --- |
| `user` | id, name, role（使用者/提需求/评审/开发） |
| `form_def` | id, name, **fields** (JSON) |
| `flow_def` | id, name, **nodes** (JSON) |
| `flow_instance` | id, flow_def_id, current_node, status, creator_id, **data** (JSON), **visible_to** |
| `agent` | id, name, description, **avatar**, **category**（业务大类）, **maturity**（装饰性标签）, **tags** (JSON), **quick_questions** (JSON), **capabilities** (JSON，见下), **skill_md**, **harness_url** / **harness_key**（留空=默认实例）, status, usage_count, flow_instance_id, **visible_to** |
| `prompt_suggestion` | id, **page_key**, text, order —— 每个页面的提示词建议，改内容 = 改数据 |

```jsonc
// form_def.fields
[{ "key":"name",  "label":"需求名称", "type":"text",   "required":true },
 { "key":"level", "label":"紧急程度", "type":"select", "options":["高","中","低"] }]

// flow_def.nodes —— 顺序节点，想加几个评审节点就加几个
[{ "key":"submit",  "name":"提交需求", "type":"填单", "role":"提需求", "form_id":1 },
 { "key":"review1", "name":"初审",     "type":"审批", "role":"评审" },
 { "key":"review2", "name":"复审",     "type":"审批", "role":"评审" },
 { "key":"dev",     "name":"开发",     "type":"开发", "role":"开发" },
 { "key":"done",    "name":"已上线",   "type":"完成" }]

// agent.capabilities —— 纯展示配置，后台手工维护
[{ "id":"web-search", "name":"资料检索", "type":"tool",  "icon":"Search" },
 { "id":"report",     "name":"研究报告", "type":"skill", "icon":"FileText" }]
// type: tool | skill | knowledge
// 用于渲染卡片能力标签 + 对话页左栏能力卡片。
// ⚠️ 已知技术债：与 CowAgent 实际挂载的工具【不绑定】。
//    选择理由：CowAgent 的工具配置(MCP/skill)有自己的格式与管理方式，
//    在本系统内重建一套映射是重复建设，代价比不一致更大。
//    代价：一定会不一致，且不一致不会被发现——没人会去核对。
//    缓解：配置表单加提示「此处为展示用，实际工具在 Evo-Harness 中配置」。
//    该还债的信号（满足其一即打通）：
//      ① 员工多到一个人记不住谁挂了什么
//      ② 配员工的人和用员工的人分开了

// agent.harness_url / harness_key —— 留空使用默认 CowAgent 实例。
// 默认全部员工同一实例；某个员工需要隔离/独占资源/接不同内网环境时填地址即可，不用改架构。

// agent.status: 草稿 / 待评审 / 开发中 / 已上线 / 已下线
// visible_to:   角色或用户 id 列表
```

**要点：**

- 改表单字段 = 改一行 JSON；加/减流程节点 = 改一行 JSON；**新增一条完全不同的流程 = 插一条 `flow_def`**
- `visible_to` 是**可见范围，不是多租户**——查询时过滤掉、前端不显示即可，**不做强制访问控制**
- 第一版 `form_def` / `flow_def` 允许直接改数据库，不做管理界面
- **只支持顺序节点。** "金额>5000才走总监"这类条件路由不做

## 3. 交互模式：AI 定意图，组件管交互

**前端核心规则，写死它。**

```
用户："帮我查上个月张三提的需求"
   ↓  ——— 模型只出现这一次 ———
AI 返回 { component: "需求列表", query: { 提交人:"张三", 月份:"2026-08" } }
   ↓
前端渲染「需求列表」这个写死的组件，带上 query
   ↓
组件自己调 GET /api/requirements?提交人=张三&月份=2026-08&page=1
   ↓
翻页 → page=2 ｜ 修改 → PUT ｜ 提交 → POST     ← 全都不经过 AI
```

**原则：确定的事不要交给不确定的东西。** 翻页逻辑是确定的，每次过模型只会更慢、更贵、更不稳定。

组件是**写死的固定几种**（需求列表、数字员工列表、审批卡片、需求详情……）；**不写死的是"用哪个组件、查什么数据"**。

**不做**：A2UI、GenUI、模型生成布局、模型输出前端代码。

## 4. AI 调用点（共四处）

| # | 场景 | 输入 | 输出 |
| --- | --- | --- | --- |
| 1 | **路由**（首页输入框先走这一步） | 用户的话 + 已上线数字员工列表及各自能干什么 | `{ route: "agent"\|"fill_form"\|"view", agent_id? }` |
| 2 | **填表单** | 用户的话 + `form_def.fields` | 字段值 JSON |
| 3 | **挑组件 + 出查询**（`resolve-view`） | 用户的话 + 可用组件清单及参数 | `{ component, query }` |
| 4 | **生成 SKILL.md 草稿** | 需求单内容 | markdown 文本 |

四处都用 structured output，都不需要 agent loop / 工具 / harness。

**路由是这四个里最轻的**——就是个三选一分类，输出可枚举因而好测。它的意义在于让「唯一入口」真正成立：**同一个输入框，问什么都行，系统帮你找对人**。没有它，用户得自己知道哪句话该在哪儿问，那是把设计者的分层强加给用户。

### 结构化输出的三层防线

| 层 | 做什么 | 备注 |
| --- | --- | --- |
| 1 | **Schema 约束**：把 JSON schema 传给模型（`response_format` 或 function calling） | 能不能用取决于内网模型，见 §8 |
| 2 | **Pydantic 校验 + 重试** | 不只校格式，更要校业务值 |
| 3 | **人确认 / 修改** | **最重要也最便宜的一层** |

```python
class 需求单(BaseModel):
    name: str
    level: Literal["高", "中", "低"]   # AI 返回"特急"会被拦下
```

第 2 层的价值主要在**业务校验**（值不在合法范围内是 AI 填表最常见的错，手写 `json.loads()` 拦不住）。

**第 3 层意味着前两层不需要做到完美**——每个 AI 输出后面都跟着人工确认，AI 填错用户改一下即可。不要为追求 100% 准确率去搞复杂的自我修正链路。


### 场景 A / 场景 B：两种不同的 AI 使用方式

| | **场景 A** | **场景 B** |
| --- | --- | --- |
| 例子 | "查上月张三提的需求" | "最近需求都集中在哪？""为什么这月通过率低？" |
| 问题空间 | 有限、可枚举 | **无限**，事先不知道会问什么 |
| 有现成 API | 有 | **没有** |
| 交互 | 一问一答 | **多轮追问** |
| 要 agent 吗 | 不要，一次调用 | **要**：调工具、多轮、可能试几次 |
| 走谁 | 模型 API 直连（上表三处） | **CowAgent** |

**场景 B 进第一版，形态是「数据分析助手」这个数字员工**——带 `query_db` 工具（经 DBX，**只读 + 白名单表**）和 `show_chart` / `show_table` 工具，跑在 CowAgent 上。不需要新增架构层，完全复用"数字员工 = skill + 工具 + CowAgent"。

**原则不变：组件仍然写死。** 场景 B 不是"让模型现场画界面"，是"给 agent 一组图表工具，它调工具，前端用固定组件渲染"。"模型只填数据，不发明布局"在两个场景都成立。

**代价**：数字员工的输出要能是结构化的（图表指令），前端消息要能渲染结构化内容，不只是文本。

**安全边界**：AI 写 SQL 查库，哪怕原型也必须限制在**只读 + 白名单表**。沿用已有 DBX 的连接级权限配置。

## 5. API 管理：不做

| 谁在调 | 能调什么由谁决定 | 要管理系统吗 |
| --- | --- | --- |
| 你的后端调模型 | 代码里写死，三五个函数 | 不需要 |
| 数字员工调工具查系统 | 在 CowAgent 里配工具 / MCP | 不需要，用现成的 |

需要 API 管理是在数字员工变多、要接的系统变多、要控制谁能调什么的时候——**第二期**。

## 6. UI 规格

> 本节是防止实现跑偏的部分，**每一条都要能一眼看出做对没做对**。含糊的需求 + 强模型 = 高质量的错误方向。

### 6.1 根本定位：数字员工是主体，流程管理是配套

**不要套「业务系统 + AI 侧栏」那个模式。** 那个模式的前提是"已有业务系统，AI 是加进去的辅助"——本产品不是。

本产品的主角就是**数字员工**；提需求 / 评审 / 开发 / 上岗这套流程，是**为了产生数字员工而存在的配套设施**。因此数字员工占首屏主位，不能放侧栏。

布局按**使用频率**排：用数字员工（高频）> 看待办（中频）> 提需求 / 开发（低频，一个入口即可）。

### 6.2 整体布局：标签页导航 + 工作台首页

| 要去哪 | 从哪进 |
| --- | --- |
| 数字员工列表 | 「查看全部 >」 |
| 提需求 | 「＋ 我要一个新的」卡片 |

#### 标签页导航（沿用模板已有的顶部标签栏）

模板顶部已有一条标签栏（`🏠 工作台 | 共享线索录入 | … 关闭全部`），**直接复用，它就是全局导航**：

```
┌──────────────────────────────────────────────────────────┐
│ 🏠 工作台 │ 合同解析助手 │ 数据分析助手 │ 需求#42 │ 关闭全部 │
├──────────────────────────────────────────────────────────┤
│                    当前标签的内容                          │
└──────────────────────────────────────────────────────────┘
```

规则：

| 动作 | 结果 |
| --- | --- |
| 🏠 工作台 | **常驻第一个标签，不可关闭** |
| 点某个数字员工卡片 | 新开一个标签，标签名 = 员工名 |
| 「查看全部 >」 | 新开「数字员工」标签 |
| 点某张待办 / 需求 | 新开「需求#42」标签 |
| 切标签 | **内容状态保留**（对话不丢、筛选不丢） |

**为什么这个模式对**：数字员工对话是**长时程**的——聊到一半要去查个待办、看张需求单，回来对话还在。用「独立页面 + 返回按钮」会丢上下文；标签页天然解决，而且模板已经实现好了。

同时开多个数字员工对话也是允许的（各自一个标签）。

### 6.3 提示词建议（紧贴输入框，跟上下文变）

作用：① 空白输入框不告诉人能问什么；② 让用户尽可能少打字。**点一下 = 把那句话填进输入框并发送。**

| 用户在哪 | 建议什么 |
| --- | --- |
| 首页 | 帮我提个需求 · 哪个员工能处理合同 · 这个月需求都集中在哪 |
| 待办列表 | 筛出这周要交的 · 哪个最急 · 这些都是谁提的 |
| 需求详情 | 跟以前的有重复吗 · 帮我写评审意见 · 大概要做多久 |

**存配置不写代码**（见 §2 `prompt_suggestion`）。

提示词有两类，第一版可统一走 AI，但要知道区别：**真问 AI**（"跟以前有重复吗"）vs **其实是快捷操作**（"筛出这周要交的" = 给列表加筛选条件，不必过模型，还更快）。

### 6.4 两个聊天入口必须分开实现（但入口统一）

**接的后端完全不同。混在一起会渗进状态管理和路由，事后极难拆。**

| | 首页输入框 | 数字员工对话页 |
| --- | --- | --- |
| 位置 | 首页顶部 | **独立标签页** |
| 性质 | **调度器**：先路由，再决定自己处理还是转交 | 执行器 |
| 接谁 | **模型 API 直连** | **CowAgent** |
| 干什么 | 路由 / 填表 / 查数据 | 让数字员工干活 |
| 有工具吗 | 没有，只有 §4 的调用点 | 有，CowAgent 的工具 |
| 接口 | `/api/ai/dispatch`（内部再分 fill-form / resolve-view） | `/api/agent/{id}/chat` |
| 会话状态 | 轻量，不必持久化 | **由 CowAgent 持有**，见 §6.7 |

**用户视角只有一个入口**：在首页输入框说任何话。路由判断后，如果该交给某个数字员工，**自动新开那个员工的标签并把这句话带过去**；否则首页自己处理（填表 / 出查询）。

> `resolve-view` 原名 `query`，改名是因为它**不查数据**，只把人话翻译成"看哪个视图、什么条件"；真正取数由组件自己调业务接口。叫 query 会误导实现者做成"每次翻页都过模型"。

### 6.5 页面清单

| 页面 | 内容 |
| --- | --- |
| 登录 | 账号 + 角色 |
| 首页 | 见 §6.2 |
| 数字员工列表 | 卡片列表（内部应用市场形态）：名字、一句话说明、能干什么、谁做的、用过多少次 |
| 数字员工对话 | **独立页面**，代理到 CowAgent |
| 需求填写 | 按 `form_def.fields` 动态渲染；AI 预填 + 人工改 |
| 需求详情 | 表单值 + 流程进度 + 操作按钮（按当前节点和角色显示） |
| 待办列表 | 复用模板；按角色显示待评审 / 待开发 / 我提的 |
| 开发任务详情 | **一个跳去 CowAgent 的入口 + 一个"skill 内容"提交框** → 标记上线 |

> "开发"这一步 = 人直接跟 CowAgent 聊，把流程试通后把 skill 固化下来。**不用做编辑器。**

### 6.6 组件库（五类，靠参数化扩展，不靠堆数量）

**这是本项目唯一需要真正设计的东西**，也是可沉淀资产——换任何流程它都能用。

**设计原则：组件越多，AI 挑错率越高。** 规模不由"想多丰富"决定，由"AI 能可靠区分多少种"决定。**丰富度靠参数化**——`chart` 一个组件带 `type` 参数，优于四个独立组件（挑错代价小、只维护一套 schema、加类型 = 加枚举值）。

按"人理解数据的几种方式"倒推，五类足够：

| 类 | 组件 | 回答什么问题 | 主要参数 |
| --- | --- | --- | --- |
| 单值 | `metric` | 多少？ | 值、标题、环比 |
| 比较/趋势 | `chart` | 谁多谁少？怎么变的？ | `type: line\|bar\|pie\|scatter`、series、坐标轴 |
| 明细 | `table` | 具体是哪些？ | 列定义、数据、分页、排序 |
| 关系 | `graph` | 谁跟谁有关联？ | 节点、边、布局 |
| 叙述 | `text` | 怎么解释？ | markdown |

**扩展时先问"能不能加个参数"，再问"要不要加个组件"。**

#### `graph` 的输入契约：组件不关心数据从哪来

```jsonc
{
  "nodes": [{ "id":"a1", "label":"合同解析助手", "type":"agent", "props":{} }],
  "edges": [{ "source":"req42", "target":"a1", "label":"相似", "weight":0.8 }]
}
```

只要给它 `{nodes, edges}`，数据来自自己的表、Neo4j 还是别的，组件一行都不用改。**这是"接口越窄越好复用"在组件层的体现**，跟管理层与 CowAgent 之间只有四个动作是同一个道理。

第一版两个用法：

| 用法 | nodes | edges | 数据源 |
| --- | --- | --- | --- |
| **重复建设检测**（服务评审） | 新需求（中心）+ 相似的已有员工 | 新需求 → 各员工，`weight` = 相似度 | `flow_instance` + `agent` |
| **能力地图**（服务管理者） | 数字员工 + 业务领域 | 员工 → 覆盖的领域 | `agent` + `agent.tags` |

**相似度第一版不上向量检索**——让 AI 直接判断"这个新需求跟哪几个已有员工像"就够，结果是给人看的，人自己会判断。

**Neo4j 是第二个数据源，不是前置条件**。单位在用但开发环境没有真实数据，等接到有数据的环境时换数据源即可。上个项目的 ECharts 图谱实现（节点属性、搜索、邻居展开、刷新）直接搬过来当实现。

### 6.7 数字员工对话页（三栏：过程 → 交流 → 结果）

```
┌──────────┬──────────────────────┬──────────────────┐
│  左栏     │      对话区           │    产物画布       │
│  240px   │      弹性             │   480–600px      │
│  可折叠   │                      │   按需展开        │
│          │                      │                  │
│ 快捷问题  │   [对话流]            │   图表            │
│ · 比较两…│   ← 真实执行记录在这里  │   表格            │
│ · 整理成…│                      │   图谱            │
│ ──────── │                      │                  │
│ 能力配置  │                      │  （累积成看板）    │
│ [资料检索]│                      │                  │
│ [记忆检索]│   [ 说点什么... ]     │                  │
│ ──────── │                      │                  │
│ 执行进度  │                      │                  │
│ ● 检索资料│                      │                  │
│ ○ 生成结论│                      │                  │
└──────────┴──────────────────────┴──────────────────┘
    过程            交流                  结果
```

信息层次 **过程 → 交流 → 结果**，从左到右符合阅读顺序。

**左栏三段（上下堆叠，不做状态切换——切换会让人找不着东西）：**

| 段 | 性质 | 内容来源 |
| --- | --- | --- |
| 快捷问题 | 常驻，点了就发 | `agent.quick_questions` |
| 能力配置 | **静态**，小卡片 | `agent.capabilities`（纯展示配置，后台维护；与实际挂载不绑定，见 §2 技术债注记） |
| 本轮执行进度 | **动态** | 由 CowAgent 的工具调用事件投影而来 |

**左栏可折叠、右栏按需展开**：1440 屏 240+600+600 刚好；没产物时右栏不占地方，对话区变宽；窄屏左栏自动收起。

#### 执行进度：可以美化措辞，不能伪造状态

把 `tool_call: web_search` 显示成"正在检索资料"——**这是必要的翻译**，用户看不懂前者。

**但必须绑真实事件。** 不要做成"固定显示三步、不管实际执行什么"：agent 真卡住或失败时，用户还盯着"正在分析…"转圈，那种恼火比什么都不显示更严重——**他会认为系统在骗他，而且那次是真的**。绑真实事件成本不高（CowAgent 本来就有工具调用事件），但它决定这块是加分还是埋雷。

左栏是**投影**，真相始终在对话流里。

#### 画布：累积成看板

新出的图表往下排，旧的留着，可横向对比；每张可单独删除。**探索式分析的价值就在对比**，只留最新一张会逼用户反复重问。实现是 append 而非替换。

**产物出画布、不嵌对话气泡**：图表是要盯着看、要对比、要带走的东西，塞进气泡又小又难比。**对话是过程，右边才是结果。**

> 第二期：「钉到工作台」——探索结果沉淀成固定看板。第一版只累积，不保存。

#### 画布里的组件可以操作，但不过 AI

表格翻页排序、图表缩放 tooltip 都是组件自己的事，直接调业务接口。**"点柱子下钻看明细"这种需要新数据的，第一版不做**——用户再问一句就行。

#### 对话历史：留，并提供「新对话」

CowAgent 持有 session，Web 端只需记住 `agent_id → session_id` 映射，下次打开续上；顶部「新对话」可重开。

> 逻辑是反的：**"留"几乎不用做事，"不留"反而要主动清 session。** 第一版不做会话列表。

### 6.8 数字员工卡片规格

| 元素 | 来源 | 说明 |
| --- | --- | --- |
| 头像 | `agent.avatar` | 不回答功能问题，但**图形识别比文字快**，且让"数字员工"具象化 |
| 分类标签 | `agent.category` | 用于筛选 |
| 岗位名 | `agent.name` | |
| 一句话简介 | `agent.description` | |
| 能力标签 | `agent.capabilities` 取前 3 | 纯展示，见 §2 技术债注记 |
| **成熟度** | `agent.maturity` | **后台配的装饰性标签**（同"精选/推荐"性质）。底线：别让用户据此把重要工作交给未验证的员工 |
| **使用次数** | `agent.usage_count` | 客观数据，与成熟度并列最好："成熟 · 本月 142 次" |
| 谁做的 | 关联 `flow_instance.creator` | 企业内部有价值——知道找谁问 |
| 进入工作台 | | |

**不放版本号**：对用户几乎无用，是内部信息。用户不关心是 V1.0 还是 V1.2。

> **设计原则：能用客观数据的地方不要用主观分级。** 主观分级需要人维护，而没人会维护它；客观数据系统自己算，永远是真的。「成熟度」是明确接受的例外（要的是感知价值）。

**不需要预置几十张**：配置表单支持上传，预置 10–20 张统一风格的够用，员工多了再补。

## 7. 技术栈

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | **沿用现有模板**：React 18 + Vite + TS + Tailwind + react-router-dom + Zustand | 用户认得这个界面；流程系统骨架（待办列表/筛选/分页/KPI卡）已有；Vite 打静态文件，内网部署扔 Nginx 即可 |
| ~~Next.js~~ | **不用** | SSR 对后台管理系统是负担，离线部署要多跑 Node 服务；麒麟+奇安信下越新的前端特性风险越大（上个项目栽在 Chromium 120 缺 `Iterator`） |
| 后端 | **Python + FastAPI + Pydantic** | ① CowAgent 是 Python，写自定义 channel 就是 Python，同一套依赖同一套部署；② 离线交付少打包一套运行时；③ Pydantic 正好是 structured output 的标准工具 |
| 图表库 | **ECharts**（新增依赖，前端） | ① 一个库同时覆盖 `chart`（line/bar/pie/scatter）**和 `graph`（关系图）**，不用再引第二个图库；② 上个项目的 Neo4j 图谱就是 ECharts graph，节点属性/搜索/邻居展开那套代码**能直接搬**；③ 离线本地资产已验证过。对比 Recharts：React 原生但**不画关系图**，图谱得另找 G6/vis.js，变成两套依赖 |
| 模型接入 | **OpenAI 兼容接口**；`base_url` / `api_key` / `model_name` 全走环境变量 | 开发用现有模型、部署接内网模型，靠配置切换，不写死。⚠️ **OpenAI 兼容 ≠ 支持 `response_format`/function calling**——很多内网服务只兼容基础 chat completions，见 §8 |
| 数据库 | **用现成的**（PostgreSQL / MySQL） | 别为这个引新东西 |
| 执行层 | CowAgent（v2.1.8，MIT，Python 3.13） | 见 §10 |

## 8. 开工前要验的两件事【待验】

**Day 0 半天做完，两件一起。**

| 验什么 | 怎么验 | 不行怎么办 | 影响面 |
| --- | --- | --- | --- |
| **内网模型的结构化输出** | 拿真实内网接口，让它按一个 JSON schema 返回，**跑 20 次看稳不稳**；确认支不支持 `response_format` / function calling | 加强校验+重试兜底，或换模型 | **大**，影响整个 AI 体感 |
| **CowAgent 能否写自定义 channel** | 拉源码读 `channel/` 基类 + 一个现有实现；确认能否「接外部 HTTP → 投给 agent → 拿回结果」；确认装/查 skill 有无可编程入口 | 退到 CLI + 文件集成（能力受限） | 小，只影响最后一环 |

**已知**：CowAgent 支持 11+ 渠道，一个实例可同时服务多渠道，架构宣称各层松耦合，但 README 未文档化自定义 channel 写法与 HTTP API。从源码目录结构（存在 `channel/wechatmp/` 一类）看，channel 应是其插件化扩展点。

> 注意：**这两项不阻塞前 80% 的开发。** 提需求→评审→开发→上线这四步完全不依赖 CowAgent。Day 0 验完，Day 1 照常开工。

## 9. 开工顺序

设计原则：**每一步结束都有能演示的东西**，不会出现"做了三周还什么都看不见"。

| 步 | 做什么 | 有 AI 吗 | 做完能演示 |
| --- | --- | --- | --- |
| 0 | 验 §8 两件事（半天） | — | — |
| 1 | 建表；首页布局（数字员工卡片位 + 待办列表 + 指标卡）；能翻页、能进详情 | 无 | 界面活了 |
| 2 | **流程跑通**：提需求→评审→开发→上线；四个角色各看各的 | 无 | **"流程通了"** |
| 3 | AI 调用点 #1：**输入框填需求单** + 人确认；提示词建议 | 有 | **"AI 帮我填表了"**（体感最好） |
| 4 | 接 CowAgent，数字员工能对话（先只渲染文本） | — | 闭环完整 |
| 5 | 组件库五类 + 结构化消息渲染 + **「数据分析助手」（场景 B）** | 有 | **"AI 自己查库出图"**（最炸） |
| 6 | AI 调用点 #2：`resolve-view` 挑组件 + 出查询（场景 A） | 有 | 说人话查数据 |
| 7 | **硬标准验收**：配一条报销流程，计时 | — | **范式成立** |

**第 1、2 步没有 AI，但它们是地基。** 流程和数据模型错了，AI 加上去也白搭。这两步必须由 `flow_def.nodes` 驱动，**一个节点都不许写死**，否则第 6 步一定过不了。

### 交给 Codex 时必须做的两件事

**一、不要说"按方案实现"，要说"先做第 1 步"。**
整份文档丢过去说"实现吧"，它会一口气全做完；等发现方向不对已是几千行之后。**分步交付、每步验收**是控制 AI 的唯一有效手段。

**二、明确要求遵守 §11「明确不做」。**
AI 的默认行为是"顺手多做一点"。不写死边界，它会给你加审计日志、权限体系、并行分支、条件路由——每样都很"专业"，每样都在挖坑。

## 10. 选型结论与被否决项

| 选择 | 结论 | 理由 |
| --- | --- | --- |
| 管理层 Web | **自研**（沿用现有前端模板） | 业务逻辑、角色、流程状态都在这，无现成可套 |

## 11. 明确不做（开发时逐条遵守）

- 生成式 UI（A2UI / GenUI / 模型输出布局或前端代码）
- 多租户隔离、强制访问控制
- API 管理系统
- 审计日志、版本管理、回滚
- skill 的资源权限声明
- 流程引擎高级能力：并行分支、会签、超时升级、**条件路由**——第一版只要**顺序节点**
- 多实例自动编排（先一个 CowAgent 实例装多个 skill）
- 离线交付包、增量更新（验证完范式再说，别再把顺序搞反）

## 12. 验收标准

**硬标准（决定成败）**

> 新配一条完全不同的流程（报销：提交 → 主管批 → 财务批 → 完成），**不改代码，一天内配完并跑通**。

**架构验收（跟硬标准同性质）**

> 开发过程中至少配出 **1-2 个真实业务的数字员工**，验证"配一个员工"确实是**配置工作**而不是开发工作。
> 如果配一个要花两天，说明架构有问题——这个问题拖到演示前才发现就晚了。

**功能验收**

- 四个角色各自跑通一遍，看到的东西不同
- 一条数字员工需求走完全程：提 → 评 → 开发 → 上线 → 被别人用上
- `visible_to` 生效：不该看到的人在列表里看不到

**AI 验收**

- 说一句话，需求单被填好，人改两个字段就能提交
- 说一句话，列表被查出来，翻页/修改/提交都不经过模型
- 结构化输出连跑 20 次，失败能被校验拦下并重试成功

## 14. 方法论（学习用）

1. **顺序**：先搭环境再想需求，是上一版最大的错。架构判断里最大的一块就是"什么时候做什么"
2. **"架构上可扩展" ≠ "生态上已经有"**：「万物皆插件」是内部架构描述，不是生态承诺。分辨方法——看生态年龄和维护者
3. **需求没进文档 = 选型对着空气做**：OA/评审/上岗/多用户在上一版 15 份文档里出现 0 次。AI 的输出质量上限由你给它的信息质量决定；模型越强，错误前提被执行得越彻底
4. **可复用性是设计时决定的**：管理层与执行层之间接口有多窄，直接决定将来能不能展开
5. **用数据模型逼自己想清楚**：自然语言可以含糊，数据模型不行。填到哪格卡住，那格就是没想明白的地方
6. **给 AI 的词决定它做多重的东西**：说"多租户"它做隔离体系，说"可见范围过滤"它加个 WHERE；反过来说"转发后端"它会做得太薄，业务逻辑无处安放。**用词精度 = 工程量控制**
7. **确定的事不要交给不确定的东西**：翻页逻辑是确定的，不要每次过模型
8. **先找阻塞未知，用最小成本验掉再开工**：§8，半天，省几周
9. **留一层人工确认，前面就不用做到完美**：产品设计能替代大量工程复杂度
10. **分步交付、每步可验收**：这是指挥 AI 做大项目的核心手段，不是效率问题，是风险控制
11. **约束要可判定**：防止 AI 做偏，靠的不是"说得更详细"，而是"说得能一眼判定对错"。「做个 AI native 的界面」它自由发挥；「侧边导航固定这 6 项，数字员工对话是独立页面只调 `/api/agent/{id}/chat`」它没法发挥
12. **AI native 不等于界面元素更少**：导航菜单回答"我能干什么"，聊天框回答不了——它是个空白输入框。减掉的东西要有人接手，否则就是把认知负担推给用户
